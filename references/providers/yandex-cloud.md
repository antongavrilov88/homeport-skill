Egress traffic beyond the free allowance is billed per gigabyte and is the line item that surprises people: the free allowance was 100 GB a month in the original notes and may be smaller now — check the pricing page — and a family watching video passes it either way. Count before you promise a price; a flat-rate VPS (`provisioning.md`, relay-capable hosts) avoids the question. |
| **Static address** | Yandex's term: **static public IP address**. The address a VM gets with **Public IP address: Auto** is *dynamic*: it is released when the VM is stopped and a new one comes with the next start (a restart keeps it). It can be **made static in place, same address** — so run the phone check on it first (`human-steps.md` §6) and make it static once it passes, before the install. Attached to a running VM a static address costs the same as a dynamic one; stopped or unattached, a reservation fee is added (`provisioning.md`, "The relay's address"). Default quota: two static addresses per cloud. |

| **Payment** | Cards of the local banking system, corporate invoices. New accounts get a starter grant — do not rely on it for the monthly figure. |
| **Known blocked ranges** | The address is domestic, which is the point — but on networks that only allow listed address ranges one domestic address gets through where another does not, which is what the phone check before the install is for (`human-steps.md` §6). What can also happen is that the provider, following local filtering orders, starts dropping the tunnel to the exit: that is why the relay profile has a watchdog that fails everyone over to the direct route and back. |
| **Firewall** | **Security groups.** A VM always has at least one: the groups picked under **Network settings** when it is created or, if that field is left empty, the network's **default security group**. What the default group lets in is not documented consistently (Yandex Cloud's documentation, read 2026-10-04, sources under the click paths): the create-VM page says it "allows connections to the VM over `SSH`, `RDP`, `ICMP`, and any outbound traffic", which leaves the relay's UDP ports closed; the security-groups page lists "All incoming (`ingress`) network traffic", then warns that it "allows incoming traffic over `SSH` and `RDP` from any IPv4 address". Either way, check which group the VM has and make sure it lets in `22` tcp, `443` udp and `51821` udp from any address (`0.0.0.0/0`): add an inbound rule for each one that is missing. Those three are the only ports the relay's installer opens on the machine (`provisioning.md`, requirements): `51821` udp is WireGuard and `443` udp the alternative WireGuard port, both opened every time. Nothing on the relay listens on `443` tcp: that is the port its tunnel to the exit uses outbound, and both descriptions of the default group allow all outbound traffic. |
| **Quirks** | The login is the user you name when creating the VM, **not root**, with passwordless `sudo`: the two lines become `scp … <user>@<IP>:~/` and `ssh <user>@<IP> 'sudo bash ~/setup-relay.sh'`. The metadata **user-data** field exists — **do not** put the relay installer in it: metadata is readable by any local process and the relay installer carries the panel code and the tunnel identifiers. Deliver it over SSH. |

## Click paths

**Account** — `console.yandex.cloud` → sign in with a Yandex ID → create a billing account → attach a card.

**VM (§6)** — **Compute Cloud → Virtual machines → Create VM** → image **Ubuntu 24.04** → availability zone: any → Computing resources: platform **Intel Ice Lake** (or whatever offers a **20%** core fraction), **2 vCPU**, **1 GB** → Network settings: **Public IP address: Auto** → Access: **Login** (a name), **SSH key**: paste the public key you generated (`~/.ssh/vpn-kit.pub`) or the person's own → Name `vpn-relay` → **Create VM**. The public IP is on the VM's page.

**Static address (§6)** — once the phone check has passed, keep that address: **Virtual Private Cloud → Public IP addresses** → the menu in the address's row → **Make static** → **Change** (CLI: `yc vpc address list` for the ID, then `yc vpc address update --reserved=true <address ID>`). If the check fails, get another address: stop and start the VM (a dynamic address is replaced on start), or reserve a static one — **Virtual Private Cloud → Public IP addresses → Reserve public IP address** → **Availability zone**: the VM's → **Reserve** (`yc vpc address create --external-ipv4 zone=<zone>`) — and swap it in on the VM's page: **Network** → the interface's menu → **Disassociate public IP address** → **Delete**, then **Add public IP address** → **List** → the reserved address → **Add** (`yc compute instance remove-one-to-one-nat --id=<VM ID> --network-interface-index=0`, then `yc compute instance add-one-to-one-nat --id=<VM ID> --network-interface-index=0 --nat-address=<address>`). The address and the VM must be in the same zone: for an address in another zone, create the VM there. A static address you do not keep: **Public IP addresses** → its row's menu → **Delete** (`yc vpc address delete <address ID>`) — it is billed until deleted, and a deleted address cannot be restored.
